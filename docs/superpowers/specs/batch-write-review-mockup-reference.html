Batch write review

One approval covering many records — where every row is visible before you sign, not after. This is the alternative to twenty separate cards, and to a blanket auto-approve that would consent to payloads that do not exist yet.

Why the row values are shown, not summarised. The approval has to attach to content you actually saw. A count alone (“approve 18 records”) is the blank cheque we are trying to avoid — it consents to whatever the extractor happened to produce.

Row 3 is the whole problem. The request was sent and NetSuite never answered — a timeout, a dropped connection, a crash between send and confirm. The record may exist. Retrying blindly writes it twice; skipping it loses a vendor. Today the system cannot tell you which.

What makes row 3 answerable

  • Idempotency key derived from the work itself (batch + row + payload hash), sent with the write — a retry cannot create a second record.
  • Side-effect log written BEFORE the call, so a crash between send and confirm still leaves a trace saying “row 3 was attempted”.
  • Reconcile on resume — query NetSuite by the key, then mark row 3 written or not-attempted from evidence rather than from a guess.

Resume, not restart

Resume is blocked until row 3 is resolved. That block is the feature: a batch that silently skips its one uncertain row is how a ledger acquires a duplicate nobody can explain.

What this replaces

Today — one card per record20 clicks
Blanket auto-approve1 click, 0 seen
This1 click, 20 seen

Auto-approve and batch review cost the same effort. They differ in what the approval attaches to: a promise about future payloads, or the specific rows in front of you. Only the second survives a mis-mapped column.
